## ADR-001: 四個邏輯元件，保留獨立餐廳介接

### Status

Proposed

### Date

2026-10-05

### Context

LINE 接收與回覆、推薦政策、本人資料權利及外部來源格式有不同變更原因。第一版雖供同事親友使用，仍需要來源故障與零結果區分、資料權利及可替換受控測試，不適合讓來源資料直接穿透到入口與歷史。[Q1][requirements FR1–FR5]

### Decision

採 LineInteraction、LunchRecommendation、DataPrivacy、RestaurantSourceAdapter 四個程式元件。LINE 呼叫推薦與資料權利，推薦呼叫介接；不因元件數推論部署服務數。介接有格式驗證、未知值與失敗辨識、來源標示等責任，不是空的轉呼叫包裝。

### Alternatives Considered

| 方案 | 優點 | 代價／可逆性 |
| --- | --- | --- |
| A：四元件，介接獨立（採用） | 外部格式與推薦政策分離，可獨立模擬及驗證 | 多一個契約；可在日後保留邊界下合併程式組織 |
| B：三元件，介接屬推薦內部 | 較少跨元件介面 | 來源替換較易牽動推薦；後續仍可抽離，但需補邊界測試 |

### Consequences

- 正面：推薦不需知道 LINE 或個人歷史，來源替換不直接更動歷史模型。
- 負面：必須維護候選、來源失敗及必要標示的契約；換來源仍需查核合法性與資料涵蓋率。
- Security and Compliance：只讓介接取得當次必要位置，不給主體識別或歷史；不默認可保存供應方內容。資料庫、LINE 與外部餐廳服務是依賴，不是自有元件。

### Alternatives Rejected

本輪未採 B，因外部格式變化及失敗辨識需要獨立測試邊界；不是宣稱三元件不可行。單體／微服務／serverless 與具體供應方不在此決策內。

## ADR-002: 同意、歷史與清除統一歸屬 DataPrivacy

### Status

Proposed

### Date

2026-10-05

### Context

保存須同時滿足受理當時與寫入時許可；撤回、重新同意、刪除與在途事件交錯不能重建舊內容。把同意與歷史分給不同擁有者，會增加跨邊界的一致性及故障組合。[Q2][requirements FR5.1、FR7–FR9、NFR2]

### Decision

DataPrivacy 擁有 ConsentState、QueryHistory、DeletionConfirmation、HistoryWriteControl、CleanupJob，其他元件只透過其介面操作。它判定可信受理順序、同意版本、範圍／截止、保存結果及到期；入口的來源驗證不取代本人授權。保存最後許可檢查與可見寫入須有可證明的序列化界線，具體機制待後續設計，不用責任集中假裝已解決競態。

原始事件時間只決定查詢時間及 UTC 一曆年期限，不單獨決定是否新查詢；可信順序與刪除截止對應由 Contract Design 證明。讀取不可見與 24 小時實體清除分開，短期控制資料七天到期不能讓已刪內容重現。QueryHistory 僅含既定白名單，技術資料另分類，不把同意歷史或控制資料永久保存。

### Alternatives Considered

| 方案 | 優點 | 代價／可逆性 |
| --- | --- | --- |
| A：單一資料權利擁有者（採用） | 關鍵許可與生命週期由同一邊界判定，易集中驗證 | 責任與測試較多；未來拆分前必須先證明一致性與失敗語意 |
| B：同意授權與歷史清除分屬不同元件 | 能各自演進 | 需額外許可版本、撤回與寫入協作契約，會改變 Q1 元件數 |

### Consequences

- 正面：所有歷史權利及保存限制有唯一責任人，推薦不能以歷史做個人化。
- 負面：DataPrivacy 故障會影響權利操作與許可確認；不能讓其他元件以快取副本自行放行。
- Security and Compliance：逐操作核對本人，拒絕跨人紀錄／分頁／確認；無位置歷史備份或匯出。儲存、副本及清除能力不滿足要求就阻擋真人保存，不以 TTL、加密或工作名稱當證據。

### Alternatives Rejected

本輪未採 B，因沒有獨立演進需求足以抵銷一致性成本。共享資料表讓各元件直接改寫不具單一歸屬，違反已確認邊界，不列為合格替代方案。

## ADR-003: LINE 互動協調當次流程，清除另行觸發

### Status

Proposed

### Date

2026-10-05

### Context

推薦與保存可能部分成功；接收 p95 一秒、LINE 接受結果回覆 p95 五秒、處理期限十秒，與刪除後最遲 24 小時實體清除不是同一個等待尺度。不保存的位置不能寫入持久佇列。[Q3][requirements NFR1、NFR4、FR7.3、FR9]

### Decision

LineInteraction 協調來源／私訊／事件驗證、取得許可、推薦、獲允許的保存與真實回覆。清單用 `sync` 表達取得當次結果的請求／回應關係，不選執行緒模型，也不讓接收確認必須等待推薦完成。DataPrivacy 接受可信後續觸發完成清除；觸發只帶必要識別，不複製位置，不增加使用者推播。

### Alternatives Considered

| 方案 | 優點 | 代價／可逆性 |
| --- | --- | --- |
| A：LINE 互動協調（採用） | 保持四元件，當次回覆與部分成功聚合有明確擁有者 | 入口責任較重，需測試取消／逾時；後續可抽出協調者 |
| B：另設查詢流程協調元件 | LINE 入口更薄，流程可獨立演進 | 增加元件與介面，第一版尚無其他入口需要共用 |

### Consequences

- 正面：推薦計算不依賴歷史，清除不拖住當次回覆；呼叫圖無循環。
- 負面：須在後續證明接收、期限、取消及記憶體位置生命週期可同時滿足。外部 LINE 不可用時不保證送達；24 小時事件窗口不代表回覆憑證有效 24 小時。
- Security and Compliance：來源或私訊驗證失敗不執行搜尋及權利操作；回覆狀態不明不能盲目重送或推播補發。清除觸發須另驗信任來源，不能成為繞過本人刪除確認的公開入口。

### Alternatives Rejected

本輪未採 B，因額外可重用性尚無需求支持。持久排隊位置及任意推播雖可讓回覆延後，卻與已核准範圍衝突，不作可行選項；不藉本決策選佇列產品或部署拓撲。

## ADR-004: 保存結果不明必須如實呈現

### Status

Proposed

### Date

2026-10-05

### Context

上游 FR4.3 的保存失敗文案存在 R-01：寫入可能已提交但確認回應遺失，若一律說未保存會誤導使用者。需求階段核准代表接受風險繼續，不是修正證據；本輪 Q4 明確確認補上不明結果。[Q4][upstream-review]

### Decision

DataPrivacy 判定已確認保存、確定未保存、保存結果不明；LineInteraction 只如實呈現。只有證實未寫入才使用「未保存」。結果不明仍提供可用推薦，提示「目前無法確認是否已保存，可稍後查看歷史」，保留本人歷史／刪除入口，不為查核拖延當次回覆。不明不是成功，也不是可盲目重試的失敗。

查核使用既有事件／歷史識別與目前授權；後續安全重試仍受去重、撤回、刪除、原始一年期限及短期控制資料期限約束，不建立新位置副本。歷史目前未查到或查閱失敗不自動證明原始提交沒有發生。Contract Design 必須定義晚到提交、取消與狀態核對的確切語意。

### Alternatives Considered

| 方案 | 優點 | 代價／可逆性 |
| --- | --- | --- |
| A：如實回覆不明結果（採用） | 不因等核對吃掉當次回覆時間，也不誤稱未保存 | 使用者可能需稍後查閱；完整刪除界線仍須攔住晚到保存 |
| B：當次十秒內先有界核對，仍不明再如實回覆 | 較有機會當次說清楚 | 占用 p95 五秒的預算，需要額外取消／核對證據；未來須另確認可達標後才改 |

### Consequences

- 正面：把推薦成果與保存證據分開，避免為簡化錯誤處理而作出錯誤隱私保證。
- 負面：契約及測試需增加提交成功但回應遺失／逾時、核對不可用、晚到提交與撤回／刪除交錯；不明結果可能短暫持續。
- Security and Compliance：核對不得越權或另留位置；本輪設計不是 R-01 已關閉的證據。上游需求及審查保持原樣，新的測試與實作需沿用 FR4.3、FR5.1、NFR2、NFR5 追溯。

### Alternatives Rejected

本輪未採 B，優先保留回覆時間與誠實狀態；失去確認就說未保存不是可行替代，因與可觀察事實不符。這是人類已確認的設計細化，不把上游未定的分支偽裝成已完成實作。

## ADR-005: 無法確認資料設定時停止當次搜尋

### Status

Proposed

### Date

2026-10-05

### Context

查詢前若完全無法讀取告知／選擇，連當次第三方位置處理是否可進行都不確定；這與查詢後的保存結果不明不同。只將保存關掉不能自動視為當次第三方傳輸已獲允許。[Q5][requirements FR2、NFR4、NFR6]

### Decision

停止本次餐廳查詢，回覆「暫時無法確認資料設定，請稍後重試」。位置不送給餐廳服務、不保存、不排隊等待恢復，依既定短暫生命週期釋放。設定更新失敗也不假稱生效。已確認選擇不保存者仍正常推薦，第一版不另建一次性查詢備援。

### Alternatives Considered

| 方案 | 優點 | 代價／可逆性 |
| --- | --- | --- |
| A：無法確認就停止（採用） | 邊界明確，不繞過告知或引入暫存位置 | 設定故障會暫時降低推薦可用性 |
| B：重新告知，取得一次性不保存選擇後重傳位置 | 故障期間可能仍能查詢 | 需新增一次性許可期限、重放防護與互動；可另行確認後再擴充 |

### Consequences

- 正面：未知設定不被預設成同意，Q4 與 Q5 分支容易分別測試。
- 負面：即使使用者原本選不保存，設定無法核對時也暫不能搜尋；故障文案需明確，避免以為必須同意保存才能用。
- Security and Compliance：不得暫存當次位置等待設定恢復、不自行轉送真人位置作探測；設定恢復後重新查詢，不能事後補存原查詢。

### Alternatives Rejected

本輪未採 B，因新增一次性授權狀態與期限超過第一版需要；直接假設未同意保存就能外傳位置不具告知依據，排除。

## ADR-006: 文字入口搭配 LINE 按鈕，權限獨立驗證

### Status

Proposed

### Date

2026-10-05

### Context

使用者需在私訊完成位置推薦與本人歷史管理，不應為刪除而另開網站，也不應只記住內部代碼。刪除範圍、有效期與真實清除狀態需要可理解文字。[Q6][requirements FR6–FR8、NFR7]

### Decision

以「歷史」「設定」「說明」文字入口搭配可用的 LINE 原生按鈕，呈現保存選擇、本人分頁、單筆／全部刪除、確認／取消與本人清除狀態。刪除顯示範圍及五分鐘有效期，過期引導重新發起；不推播。LineInteraction 負責繁中呈現與動作解讀，DataPrivacy 負責本人、範圍、期限及真實狀態判定。

### Alternatives Considered

| 方案 | 優點 | 代價／可逆性 |
| --- | --- | --- |
| A：文字入口加按鈕（採用） | 降低輸入負擔，確認與取消可直接操作 | 要驗證 LINE 訊息形式、長度、相容性與過期按鈕 |
| B：純文字命令 | 較容易以文字測試，不依賴按鈕樣式 | 指令輸入及記憶負擔較多；後續仍可加按鈕 |

### Consequences

- 正面：文字仍說清楚未知、不足、未保存、清除中及完成，不只靠顏色或圖示；時間用 Asia/Taipei，地圖對應實際搜尋點或餐廳。
- 負面：不能只驗證畫面能點；過期、取消、重複及跨人按鈕／分頁識別均需負面測試，文字命令與按鈕需一致。
- Security and Compliance：按鈕、紀錄識別、範圍及分頁參數均不能當授權；每次操作再驗本人及可見性。主動查閱狀態不轉成推播或其他人的歷史查詢。

### Alternatives Rejected

本輪未採 B 作唯一入口，但保留文字提示與入口。具體命令格式、LINE 訊息型式及錯誤回覆由 Contract／Functional Design 定義，不提前選 Rich Menu、Flex 模板或其他 UI 實作。

## Assumptions & Open Questions

- 以上方案不預選部署拓撲、雲端或儲存產品，不能當成資源、費用或真人位置處理授權。
- 四元件的許可／受理／刪除順序、不明提交與清除狀態契約仍需具體化；外部平台日誌、複本、清除與回覆能力須驗證，未驗證不能宣稱既定時限已達成。
- 所有驗收證據留給後續實作與測試：包括原始時間一年邊界、七天控制資料清除後不重生、24 小時實體清除、跨人拒絕、取消、來源及 LINE 故障與至少 80% 行覆蓋率。
- 無新的未確認產品假設；requirements OQ1–OQ10 依原責任及時點保留，不用本文件抹去已接受風險或未知條件。
